# AutoUpdate app connector contract v1

The common updater stores immutable, verified package versions and atomically changes one `current.json` pointer per app. The app reads the selected version from the returned package path. Before loading or activating any package content, call `Get-AuVerifiedCurrent`; it verifies the current pointer against the manifest and rechecks every payload size and SHA-256. A missing, altered, or inconsistent package is rejected. It must never execute files from the shared source checkout or from a staging directory.

A language-neutral bootstrap is available as `tools/autoupdate.ps1 -Command resolve -StateRoot <path> -AppId <id>`. It prints one JSON object with `schema: 1`, `status`, `app_id`, `version`, `mode`, `package_path`, `verified`, and `manifest`; exit code 0 means the package resolved, 1 means validation or invocation failed, and 2 means no package is installed. Apps may read the returned package path but must still implement their own activation and UI-state hooks.

Each connector supplies its stable `app_id`, platform architecture, writable per-user `StateRoot`, current app version, and the hooks `canApplyLive/deferReason`, `prepareLive`, `commitLive/rollbackLive`, `saveUiState/restoreUiState(schema)`, `onUpdateConfirmed`, and `onUpdateFailed`. The current core exposes `Install-AuPackage`, `Get-AuCurrent`, and `Get-AuVerifiedCurrent`; the connector remains responsible for app-specific UI state and the actual live/restart boundary.

Live submarine patching is the default. If a package omits `mode`, both the core and packager select `live` for data/resources and `restart` only when executable/runtime files make an in-place change unsafe. For a `live` package, every entry must be data or a resource, and the app must declare the compatible schema and a safe activation point. The connector switches resources as a complete set and keeps the current process, windows, unsaved input, timers, and work state intact. A package containing executable or updater-runtime code cannot be marked `live`. A live package is prepared and fully verified before activation; `canApplyLive` may defer it until an app-defined safe point, keeping the old complete set active.

For a `restart` package, the app first captures and durably writes its UI/work state, then invokes `tools/restart-apply.ps1` from the installed AutoUpdate engine package with the verified app package path, executable-relative path, target, parent PID, state file, working directory, and app arguments. The helper re-verifies the package and executable hash, stages and atomically replaces the target after shutdown, then launches it with `--autoupdate-state`, `--autoupdate-health`, and `--autoupdate-version`. The app must restore its saved UI/work state and write the exact version to the health file only after recovery succeeds. If startup/restoration fails or times out, the helper restores the previous executable and relaunches it. The updated program reopens the exact prior screen and restores settings, draft input, selected tab, scroll/focus, and in-progress state before acknowledging health. Only then may the previous executable be retired. If startup or restoration fails, return to the previous version and state. User settings, credentials, cache, and user data are outside package paths.

The engine core is loaded by versioned path, not copied into each app. Updating the common engine installs a new immutable engine version and switches its pointer. Connectors reload it at a safe update boundary. An app needs a one-time connector integration; existing apps without it do not receive common-engine changes automatically.

The package schema uses SHA-256 and an explicit publisher policy. Production downloads must come from the configured GitHub release API over validated HTTPS; credentials are read from Windows Credential Manager and are never included in app configuration, arguments, logs, or package files. File/temporary package installation is reserved for local verification.

## Optional shared modules

Apps may declare reusable dependencies with `autoupdate-app-modules-v1` (`contracts/app-modules-v1.schema.json`). Call `tools/autoupdate.ps1 -Command resolve-modules -AppManifestPath <app.json> -StateRoot <shared per-PC state root>` at the app's configured update check. The default local source is `\\H255\AI-Work\제작중인 프로그램\AutoUpdate\outbox\modules`. The result lists verified immutable module paths cached under the common per-PC `StateRoot`; apps using the same module ID share those bytes and each PC downloads its own copy once.

The app adapter must validate the resolved API major and activation mode. A changed module path affects future loads only. To patch currently loaded code without closing the app, the adapter must reach a safe point and invoke its real reload hook while preserving the current UI and work state. If it cannot unload/reload code safely, use `restart` and the state-preserving restart contract above. Apps without this one-time dependency and activation integration do not receive module changes automatically. The local pilot uses `local-share-v1`; do not treat the module directory as a GitHub release or as a signed publisher identity.
